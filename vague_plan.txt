The CLI Chassis Telemetry Tracker: Initial Spec

Building this in Crystal for the terminal is the exact right structural play. A web UI introduces too much friction when you just want to log the payload and get out. The terminal is instant, and Crystal gives you a compiled binary that executes in milliseconds.

Here is the architectural noodle for the core logic, focusing strictly on the data flow and the reporting interface.

1. The Data Architecture (The Database Schema)

To make the reporting engine fast, we need a relational structure. An embedded SQLite database via a Crystal shard is the most bulletproof way to handle this without running a separate server.

Table: targets (The Armor)

id

name (e.g., "Quadriceps", "Anterior Tibialis", "Rotator Cuff")

is_tracked (Boolean: Allows you to mute groups you don't care about)

decay_threshold_days (Integer: How many days until this group is considered "neglected")

Table: movements (The Library)

id

name (e.g., "Seated DB Overhead Press")

primary_targets (Array of Target IDs)

secondary_targets (Array of Target IDs - optional, for stabilizers)

Table: sessions (The Log)

id

timestamp

notes (Optional, e.g., "Hip feeling squishy, skipped depth")

Table: sets (The Payload)

id

session_id

movement_id

weight

reps

rpe (Rate of Perceived Exertion: 1-10)

2. The User Experience (CLI Commands)

The UI has to be zero-friction. If it takes more than 10 seconds to log a workout, Grog will stop doing it.

$ tracker status

Action: The primary dashboard. Queries the database, joins the sets to the movements to the targets, and calculates the delta between Now() and the timestamp of the last set.

$ tracker log

Action: Triggers a fast, interactive prompt.

Flow: Select Movement -> Input Weight -> Input Reps -> Input RPE -> Repeat or Save.

$ tracker library

Action: CRUD interface to add new exercises and map them to the targets table.

3. The Reporting Interface (The "Status" Output)

This is the core deliverable you requested. When you run $ tracker status, the terminal should output a color-coded matrix. The logic engine calculates the "Decay Status" based on the last time a target was hit.

4. The "Smart" Logic Engine

To make this an actual engineering tool rather than just a dumb spreadsheet, the reporting engine needs a few specific rules:

The RPE Filter: If you log an exercise, but the RPE is a 3 (a warm-up or a half-hearted attempt), the system should not reset the "Last Hit" clock. A muscle group is only considered "targeted" if the RPE crosses a certain threshold (e.g., RPE 6 or higher). You only get credit for actual mechanical tension.

Primary vs. Secondary Weighting: (Optional V2 feature) The system could differentiate between hitting the triceps primarily (Skullcrushers) vs. secondarily (Overhead Press). For V1, a hit is a hit.

This structure maps exactly to the matrix we built earlier. You define the chassis components, you map the tools in the library, and the terminal yells at you in red text when a piece of the armor is actively decaying.
